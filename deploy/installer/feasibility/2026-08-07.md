# Phase-zero Cloudflare installer feasibility — 2026-08-07

## Decision

**NO-GO for U7 broker implementation.** The phase-zero falsification tests established useful platform contracts, but neither R43 nor R46 satisfies the accepted implementation gate. U1-U6 remain valid, and the advanced manual deployment path remains the supported Access path while the gaps below are resolved.

This record contains no OAuth credential, recovery credential, Cloudflare account identifier, email address, authorization code, state value, publisher-verification value, or customer PII.

## Test boundary

- Tested against one existing Cloudflare account with Workers, Containers, and an existing Zero Trust organization.
- Used disposable Workers, container applications, OAuth grants, and probe resources with unique names. Every resource created by a probe was removed by recorded ID or by the exact disposable Worker name.
- Used a private, unverified preview OAuth client. It is sufficient to falsify parts of the API contract, but it is not the public verified-publisher client required by R46.
- The authorization-code exchange used an exact HTTPS callback, one-time signed state, S256 PKCE, a server-side client secret, `Secure`/`HttpOnly`/`SameSite=Lax` callback state, manual redirect handling, and no browser token storage.
- The probe disabled Worker observability and returned only status codes, non-sensitive counts, and sanitized Cloudflare error code/message pairs.

## R43 — customer-owned container artifact

### Proven in the current account

- The existing Chickpea container-backed sandbox can run from an immutable image digest in the customer's Cloudflare registry.
- Baseline image digest: `sha256:ec94e23399c2e7b00c1ca951fa73a3ae674bef08f12ec4d167f11451daae66b5`.
- A cold-start probe ran Node `22.23.1`, Python `3.10.12`, and emitted the expected `chickpea-r43-ok` marker.
- A synthetic rollout image was published at digest `sha256:08288c9f3392cd2adf2cd6f030a5364c3ee227a0d762054f649938540de7eee9`, rolled out, exercised, and rolled back to the baseline digest.
- The code update reset the disposable sandbox Durable Object once; the next invocation recovered and passed. This is expected rollout behavior that the release contract must expose rather than hide.
- The synthetic rollout tag and disposable Worker/container application were removed. The baseline release image was retained.

### Not proven

- A second customer account can receive the immutable image through a supported source-to-customer distribution path without depending on Chickpea-owned runtime infrastructure.
- A new or non-entitled account reports a deterministic Containers entitlement failure before mutation.
- First pull, rollout, rollback, and cleanup work across the required account/plan fixture matrix.
- The signed release manifest can describe a portable image source without embedding one customer's registry coordinates.

### R43 result

**Partial pass in one entitled account; gate failed.** Before U7, either:

1. prove supported cross-account customer-owned image distribution and the missing entitlement fixtures; or
2. make the product decision allowed by KTD23 to launch one-click without the container coding tier and disclose that limitation before OAuth.

Cloudflare OS's public release manifest does not deploy a Containers artifact, so its one-click flow is not evidence for Chickpea's container ownership model.

## R46 — OAuth and Zero Trust provisioning

### Exact preview permission set

The private preview client requested exactly these ten scopes:

| Cloudflare consent label | OAuth scope |
|---|---|
| User Details Read | `user-details.read` |
| Account Settings Read | `account-settings.read` |
| Workers Scripts Read | `workers-scripts.read` |
| Workers Scripts Write | `workers-scripts.write` |
| Workers Containers Read | `containers.read` |
| Workers Containers Write | `containers.write` |
| Access: Apps and Policies Read | `zone-access.read` |
| Access: Apps and Policies Write | `zone-access.write` |
| Access: Organizations, Identity Providers, and Groups Read | `access-acct.read` |
| Access: Organizations, Identity Providers, and Groups Write | `access-acct.write` |

The consent screen bound each grant to exactly one selected account.

### Proven operations

| Capability | Endpoint or provider action | Result |
|---|---|---|
| Authorization code + S256 PKCE | Cloudflare OAuth authorization and token endpoints | Pass |
| User and selected-account inventory | `GET /user`, `GET /accounts` | Pass; exactly one selected account returned |
| Worker inventory | `GET /accounts/{account}/workers/scripts` | Pass |
| Immutable Worker ID inventory | `GET /accounts/{account}/workers/workers` | Pass |
| Worker create/delete | `PUT`, `DELETE /accounts/{account}/workers/scripts/{script}` | Pass through the OAuth grant |
| Container application inventory | `GET /accounts/{account}/containers/dash/applications` | Pass |
| Access application inventory | `GET /accounts/{account}/access/apps` | Pass |
| Access organization inventory | `GET /accounts/{account}/access/organizations` | Pass |
| Access identity-provider inventory | `GET /accounts/{account}/access/identity_providers` | Pass |
| Access-token revocation | `POST https://dash.cloudflare.com/oauth2/revoke` | Pass; a harmless `/user` reuse returned `403` |
| Two concurrent grants | Two independently stored server-side grants for the same selected account | Pass; revoking grant A made A unusable while B remained usable, then B was independently revoked |

The private client issued no refresh token and did not permit `offline_access`. A production public-client grant and its renewal/expiry semantics remain unproven.

### Failed or incomplete operations

#### Access application write

`POST /accounts/{account}/access/apps` returned HTTP `403`, Cloudflare API error `1010`, with no diagnostic message.

The result reproduced with:

- the intended path-shaped public destinations;
- a minimal self-hosted application payload; and
- a minimal application targeting the disposable Worker's immutable ID with a `worker` destination.

The same grant could read Access applications and could create/delete the disposable Worker. The Cloudflare consent UI explicitly labeled `zone-access.write` as **Access: Apps and Policies Write**. Therefore the current evidence isolates an unresolved OAuth/Access-write limitation; it does not establish whether the cause is preview-client visibility, publisher verification, account policy, or a Cloudflare platform defect. Do not code around it or broaden permissions without a provider-supported explanation and a passing public-client fixture.

Because the application could not be created, policy creation, audience discovery, path precedence, protected `/admin` plus `/admin/*`, and public callback reachability were not proven.

#### Dedicated email method

`POST /accounts/{account}/access/identity_providers` for a second `onetimepin` provider returned HTTP `409`, error `12132`: an OTP connection already exists.

The existing OTP provider was readable and could be identified, but reusing it would not satisfy R48's separately identifiable Chickpea email-method contract. Renaming or mutating the existing account provider would violate the unrelated-resource boundary. The consumer contract needs a supported dedicated method, a revised shared-method contract accepted as a product decision, or a preflight block to the advanced manual path.

#### Missing fixture coverage

- No public-visibility OAuth client under a verified Chickpea publisher domain was exercised.
- No untouched account proved Zero Trust organization creation or the bounded Free-plan enrollment handoff.
- No insufficient-role, public-OAuth-disabled, missing-entitlement, or second-account fixture was exercised.
- Organization creation was deliberately not attempted against the existing organization.
- Container writes through the exact OAuth grant were not exercised; the R43 mutations used the authenticated Cloudflare development toolchain.
- Install, upgrade, and cleanup still need distinct exact permission allowlists. The matrix above is only the preview install candidate.

### R46 result

**Partial pass; gate failed.** Selected-account binding, Worker mutation, inventory, exchange security, per-grant concurrency, and provider-observable revocation are viable. Access application/policy creation, dedicated email identity, untouched-account enrollment, public verified-client behavior, and the required account fixture matrix are not viable or not yet proven.

## Architecture consequences

- Keep Cloudflare Access behind the existing authenticator adapter. Nothing in this probe changes the shared Chickpea user, membership, role, invitation, principal, or authorization model.
- Keep the normal teammate lifecycle entirely inside Chickpea. Do not add per-user Cloudflare policy mutations.
- Do not expose Zero Trust details to normal OSS users to compensate for the failed gate. The manual dashboard path remains an explicitly advanced fallback.
- Do not implement the hosted broker against assumptions from Cloudflare OS. Its hosted deploy service is useful product/design prior art, but its private control-plane implementation and product resource graph are not the Chickpea contract.
- A future Hosted Chickpea can replace Access/session authentication and add OIDC, SAML, and SCIM while reusing the identity and authorization domain already implemented in U1-U6.

## Required evidence before changing this decision

- [ ] Verify the publisher domain and exercise a separate public preview OAuth client with the same exact scopes.
- [ ] Obtain a Cloudflare-supported explanation for API error `1010` and pass Access application plus policy creation through the public client.
- [ ] Prove a dedicated email method that meets R48 without altering unrelated providers, or explicitly revise R48 as a product decision.
- [ ] Exercise an untouched account, an enrolled account, a non-entitled account, an insufficient-role account, and a second simultaneous account fixture.
- [ ] Prove organization/IdP/application/policy create, inventory, reconciliation, cleanup, and unrelated-resource fingerprint preservation.
- [ ] Prove the R43 cross-account immutable image path and entitlement failures, or approve a containerless initial one-click release.
- [ ] Replace the preview permission list with passing install, upgrade, and cleanup allowlists and provider-observable revocation evidence.
