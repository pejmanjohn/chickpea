# Workspace management MCP

This runbook covers Chickpea's requester-bound workspace control plane: the public MCP used by coding agents and the matching Flue tools available to Chickpea in Slack. Both are adapters over `WorkspaceManagementService`; neither owns separate permissions or mutation rules.

## What is exposed

The deployment publishes an OAuth-protected MCP at `https://<chickpea-origin>/mcp`, protected-resource metadata at `/.well-known/oauth-protected-resource/mcp`, and authorization-server metadata through Better Auth under `/api/auth`. The product scope is `chickpea:workspace`.

The 401 challenge, the protected-resource metadata, and the MCP permission
check name only `chickpea:workspace`. MCP 2026-07-28 asks resources to keep
`offline_access` out of the challenge and metadata, and leaves renewal to the
authorization server. Chickpea's authorization server issues a refresh token to
every client registered for the `refresh_token` grant. A client that follows
the challenge asks for `chickpea:workspace` alone; the server adds
`offline_access` to that authorization request, and consent shows that the
agent stays signed in. A client can also request
`chickpea:workspace offline_access` itself, as `chickpea-cli` does. A client
registered without the `refresh_token` grant gets no refresh token. Access
tokens last 15 minutes; refresh tokens last 30 days and rotate on use. The
real-handler regressions in `tests/management-oauth-refresh.test.ts` verify
renewal after access-token expiry, renewal for a client that requests only the
challenge scope, resource binding, and clients without renewal.

Older deployments advertised the refresh grant but rejected `offline_access`,
so their clients received no refresh token. Update the server before signing
in again. Existing clients registered with only the workspace scope need a
fresh client registration as well as fresh consent; clearing only an expired
access token cannot repair that registration. Use the client's normal controls
to reset only this Chickpea connection, preserving other MCP servers. Codex
registers again with `codex mcp login chickpea`. In Claude Code, use `/mcp` →
`chickpea` → Clear authentication, then authenticate again. Claude versions with
the terminal commands can use `claude mcp logout chickpea` followed by
`claude mcp login chickpea`. Merely re-authenticating can preserve the old client
registration. CLI `doctor` reports missing refresh support independently of
initial sign-in. A connection approved before the server added renewal to
workspace-only requests asks for consent once more on its next sign-in.

The MCP tool surface (`FIVE_ZERO_TOOL_NAMES` in `src/management/mcp-v5/tools.ts`) is the 5.0 tools, the same 59 for every client:

- the first 5.0 tools, added beside the 4.x tools in 4.3: `get_account`, `get_workspace`, `list_agents`, `get_agent`, `list_services`, `list_models`, `list_members`, `list_slack_channels`, `get_agent_memory`, `list_schedules`, `get_setup_status`, `export_agents`, `list_connected_apps`, `propose_agent`, `propose_agent_change`, the card-only `get_creation_status` and `decline_change`, and `explain_agent` and `check_agent` (`src/management/mcp-v5/`). `list_agents` leaves archived Agents out unless `includeArchived` is true. Each entry is what a list needs: `agentId`, handle, the description on one line cut at 100 characters, status, `canEdit` and `needsAttention`; `get_agent` has the rest, the links included. One page, its text block and `structuredContent` together, stays within 20,000 characters, and `nextCursor`, sent back as `cursor` with the same filters, starts the next page. The Agents the caller can edit come first, then shared ones, each group in `agentId` order, and the cursor names the last one listed, so an Agent created or archived between pages never skips or repeats another; only an Agent whose own edit rights change during a read can be listed twice or left out of it. An offset cursor from an earlier Core is refused with `invalid_input`, and the client starts again from the first page.
- `get_service`, added in 4.5 beside `list_services` (`src/management/mcp-v5/services.ts`): what one catalog service can do before it is connected, from the catalog alone. A managed service lists its capability headers' tools as `read` or `write`, with a write's side-effect label; an MCP preset says `capabilitiesKnown: 'after_connecting'`, since its server lists tools only after sign-in; an API preset lists its methods and hosts. `practice` says what a practice run can use: a managed service's reads (`reads_ready`); a catalog MCP service's tools once the ones that only read are marked (`needs_read_marks`), with `update_connection` `readTools` after it is connected, and for a reviewed connector (Bugsnag, Meta Ads) by choosing its tools on the Agent's page in Admin, which its `nextStep` says instead; or an API's GET and HEAD requests (`get_only`). `not_in_practice`, nothing because none of its actions only reads, is kept for a managed service with no read; no catalog service has that today. Any signed-in person can call it; an unknown service is `not_found`
- the first 5.0 writes, added in 4.4: `create_agent`, `update_agent`, `update_agent_memory`, `archive_agent`, `restore_agent`, `add_agent_to_channel`, `save_channel_settings`, `import_skill_from_github`, `upload_skill_files`, `set_agent_skill`, `save_schedule`, `pause_schedule`, `resume_schedule`, `run_schedule_now`, `take_over_schedule`, `set_workspace_model`, `connect_model_provider`, `confirm_change` and `undo_change`
- the rest of the 5.0 writes, added in 4.5: `connect_service`, `reconnect_service`, `update_connection`, `remove_connection`, `remove_website_login`, `set_agent_repositories`, `delete_agent`, `remove_agent_from_channel`, `delete_schedule`, `remove_model_provider_key`, `update_member`, `cancel_setup_link` and `disconnect_app`
- the practice run tools, `practice_agent`, `get_practice_run` and `list_practice_runs`, added in 4.5 beside `get_creation_status`
- `get_guide`, added in 4.6 (`src/management/mcp-v5/guide.ts`): one section of the playbook below, for every client
- `show_test_report`, added in 5.1.0 (`src/management/mcp-v5/test-report.ts`): the report card of a test drive, called after each round since 5.2.0

`practice_agent` runs one of the caller's Agents once, as the caller's direct message would run it, read-only: it makes only read requests and sends nothing to Slack. It asks the question it is sent, or, with none, the first question stored when the Agent was created (`config_agents.first_ask`). `get_practice_run` reads a run by its `runToken`. The cards call `practice_agent` with no question, then `get_practice_run`. Each needs a deployment serving many installations, because the installation's state store erases the run's Flue instance with the host erase; Node and a standalone Cloudflare deployment return `test_run_unavailable`, which is not retryable, so the card offers Open in Slack and no Try again. Before a run starts it refuses an Agent the caller cannot change (`not_allowed`, or `not_found` for one they cannot use, which also covers a deleted Agent and reads "That Agent is gone, or you can't change it."), a question holding a key (`invalid_input`), a caller Slack would not let message the Agent, a model that cannot run, an Agent with no stored first question when none is sent, and a personal connection the caller has not signed in to (`needs_setup`). Who may message the Agent is decided as a direct message's run decides it, read only: Chickpea's own admission, then Slack's record of the person and the Agent's private Channels, each answered within 5 seconds. A refusal is `not_allowed`; Slack's silence is `temporarily_unavailable`, never an admission. A connection with no tool an Admin declared a read is left out of a practice run, listed under `off` with its fix in `fixes`, and in `leftOut` as `{ service, fix? }`, which no fit cuts, and the run says `partial: true`; a card draws the answer and what the run read, never `off`, `steps` or raw results. For a custom MCP connection the caller may change, the fix is `update_connection` naming that connection, and the next step tells the model to ask the person which tools only read and to mark only the ones the person confirms, never from a tool's name; a member refused a team connection is told an Owner or Admin can mark them. A ready one that allows no tools, or whose allowed tools all say they change things (their server's stored hint, which `update_connection` refuses to mark as a read), has nothing to mark, and `get_agent` names no tool to allow, so its fix is the Agent's Admin page, where its tools are chosen. A managed service, or a reviewed connector such as Meta Ads or Bugsnag, added from the catalog or by its URL, keeps the Agent's Admin page, whose tool choices can add a read, and gets no `update_connection` fix, which `update_connection` would refuse. A refusal with that fix doesn't end "Ask {Agent} in Slack instead.", because the card follows the fix with "Finish on the Chickpea page that opened, then try again."; one with no fix keeps it. A catalog MCP service gets the custom one's fix, `update_connection` naming it, from whoever may change that connection; one that allows no tools, or only tools that say they change things, gets no fix, because Admin chooses no catalog service's tools. Nothing counts a person's runs: the plan's funding refuses one as it would refuse that direct message, in its own words. A retry with the same `idempotencyKey` and question returns the same run before any check, and a key sent with another question starts a new run under a key the server mints. The same person's same question to the same Agent returns the run that is going, or, for 2 minutes after it answers, that answer with `repeat: true`, while the compiled plan is unchanged; an edit to the Agent's instructions, model, connections, read marks or memory changes the plan, so the question runs again, and so does a question whose last run failed. A first question starts a practice conversation, and `practice_agent` with that result's `practiceId` asks a follow-up in it. The state store writes a follow-up's message from its own rows of the caller's conversation, so a client sends only the ID: "Earlier in this practice conversation (quoted):", each earlier answered turn's question and reply behind `> `, under each reply one line naming what that turn read by service, tool or request method (the one the request's own arguments asked for, recorded on the step when the run settles) and outcome (`Read: Probe Board (probe_board_search, ok); Release API (GET, refused)`), ending `…and N more calls` for a turn with more calls than its 25 steps, never what it returned, then "New question:" and the question, all escaped as a person's Slack text is (`src/agents/practice-history.ts`). A failed turn is left out, and the quoted turns keep to 48 KB, the oldest dropped first. Each turn keeps its text for its own hour from its settlement, so a follow-up quotes only the answered turns still kept. When either drops answered turns, the result's `droppedTurns` says how many, and its next step says the Agent didn't see them, being too long or too old, and to start a new conversation to ask about them. The history goes in the user message; the framing stays the last system instruction and, for a follow-up, says earlier turns are quoted and their reads must be read again. Each question is compiled and run on its own, so a follow-up after an edit runs the edited Agent. A conversation takes 10 questions, each within an hour of its latest answer (with none answered, of the end of its first turn), however long its first turn took; past either, or for a `practiceId` that is another person's, another Agent's or unknown, the refusal is `not_found`, "This practice conversation has ended. Start a new one." Its turns run one at a time: a follow-up while the last is going is `in_progress`, with that turn's `runToken` in the next step and a `get_practice_run` fix, however long that turn has run. `list_practice_runs` returns the caller's own practice runs of an Agent they can change that they can still read, as `get_practice_run` reads them (each one going, or settled within the last hour), newest first and at most 20: `practiceId`, `runToken`, `turn`, `when`, `status`, the question cut at 200 characters and `agentVersion`, never a reply, step or result, and never another person's runs, an Owner's call included. `practice_agent` returns `running` with a `runToken` 15 seconds after the call starts if the run has not settled, its admission included, and `get_practice_run` waits up to 20 seconds more on each call. A result carries everything in `structuredContent`: the reply, cut at 6,000 characters; `ran` (the Agent's version, model, effort, memory and the skills it loaded); its first 25 tool calls and skill loads as steps, each raw result labelled as data and cut to `min(1,500, floor(12,000 / results))` characters under Chickpea's cut line, and the count of any calls after them in `moreSteps`; `usage`; `off`, `leftOut`, `available` and `fixes`. A step's `outcome` is `refused` for a call Chickpea refused, a `read_web_page` or `web_search` refusal included, and `failed` for one that went out and brought nothing back, such as a page that answered an HTTP error or a search that timed out, each with Chickpea's own sentence in `why`; the tool's own words stay in `result`. A listed step's result that was cut is also kept whole, as the Agent read it after the step's exclusions and redaction, beside the run in `management_test_run_results`: first step first, up to 400,000 characters for the run, where the result that spends that total keeps its start and later ones only their excerpts. An answer with a cut result says so in its next step. `get_practice_run` with `step` (its number in `steps`, from 1) and `offset` returns that result's next part in place of the answer, at most 20,000 characters, as `stepResult` with its label, `size`, `offset`, `nextOffset` while more is kept, and `kept` when Chickpea kept fewer characters than `size`; a result its excerpt holds whole reads from the excerpt. Only the caller reads it, while they can read the run, and its part is cut further when JSON would take it past the budget. The text block carries the reply's first 600 characters, one line per step with no data, `off`, a line naming `before` and its `runToken` when there is one, and the next step, because Claude Code shows its model only `structuredContent` and Codex and ChatGPT show both blocks. Both blocks together stay within 28,000 characters, inside the 10,000 tokens ChatGPT's model reads of a result; past that, the question is cut first, then the inputs, the raw results, `available`, `off`, and the reply last (`src/management/mcp-v5/test-runs.ts`). Admission reads only the tested Agent, never the workspace snapshot, so its cost does not grow with the workspace's Agents. A run's usage is a `test_turn` operation, charged as a direct message from the caller, and Admin Usage shows it as "Practice run", under "Practice runs" by person. A practice run is bounded as a direct message to the same Agent is: the same Flue durability (10 attempts, 155 minutes), the same 6 page reads and 4 searches a turn, and no limit on its tool calls. A run stopped at its deadline, or whose instance is lost, is credited back every time, as a direct message's is: nothing bills, limits or credits a practice run differently. Like a direct message's, a run that fails while its installation refuses work is never credited back, so a run `cancel_pending` stops on a suspended installation, or erasure on an ended one, keeps its model spend and task fee, as such a direct message does. A failed or interrupted run, a direct message's or a practice run's, reports no usage, so its measurement's estimate is the sum of the list prices of the model requests under its billing run ID, once every one is priced, a request that ends after the terminal included (`UsageStoreLogic.priceUnreportedRun`); a deployment with estimates off keeps it unpriced. Its reply goes back to the MCP client, never to Slack, and carries what the caller's connections read, with each image turned into its alt text or its plain address and raw HTML escaped outside code (a top-level fence, and the code spans of a paragraph whose backticks all pair on their own lines); a run is never copied for Help improve Chickpea. Only the caller reads a run, while it runs and for an hour after it settles; then the store erases it, its question, reply and steps, the results kept beside it, and the row itself, on an alarm wake it arms for that hour. Each erase also takes any kept result whose run can no longer be read, so none outlives its run's text. A run whose instance is not erased by then loses its text at the hour and its row once the instance is erased. Once a run settles, no new or resumed attempt gets model access; an attempt already running stops at the store's abort (5 seconds past Flue's timeout, or on a cancellation), at Flue's timeout, or at its next model request once the workspace is suspended. The store fails a run still unsettled 30 seconds past Flue's timeout, and erases its instance at the latest 7.5 minutes after that. A run that never had a submission while it was live never ran, so its instance is erased 10 minutes after it was asked; until then it holds restore preparation and erasure's drain, and `cancel_pending` does not release it sooner. The store's side is `src/state/test-run-lifecycle.ts`. Its alarm looks every 10 seconds while any run's instance is not erased. A failed erase is retried at each of those looks with no end, and restore preparation refuses with "a test run not yet erased" until one succeeds; the store logs each failure as `test_run_erase_failed`.

`show_test_report` takes an Agent, 1 to 10 of the caller's practice runs by `runToken`, one for each question asked so far, each with the model's `verdict` (up to 120 characters; the card shows 40), an optional `note` (400; shows 160) and `before` (its earlier verdicts, 400; shows 100), a `summary` (400; shows 200) and an optional `next` (400; shows 160). Since 5.2.0 it also takes `round` (1 to 20), up to 8 `changes`, each a `what`, a `why` and an optional `effect` (400 each; `what` and `why` show 160, `effect` 100), and `final`. Chickpea cuts each to one line of what the card shows, ending in an ellipsis, so a report a little over is drawn, not refused. It reads only. Each run it can read must be of that Agent, and answered or failed; the refusal for the first that isn't names it by its place in the list and its `runToken` (`invalid_input` or `in_progress`). A run the caller can no longer read (past `get_practice_run`'s hour, or not theirs) draws as a row with `gone: true`, an empty question and no answer, and the result's next step names those questions, so a loop longer than an hour still gets its report. Chickpea fills in each question, cut to one line of 300 characters, from its own records, and the result carries each answer as the store kept it in `_meta["chickpea/answers"]`, which a host gives the card and never its model, so the report card draws from the result after the runs are erased and the model's context holds only its own verdicts (`cardOnly` in `src/management/mcp-v5/tools.ts`). Verdicts, notes and changes go back in the result and are never stored; the input refusal telemetry records field paths only. The model calls it after round 1 and after each change it has tested, each time with every question so far, and with `final` on the last call. Each call is the whole report, so the card keeps nothing between calls: Codex and chatgpt.com both keep one card per tool in a turn and redraw it at the latest call (measured 2026-11-13). While a `round` is set and `final` is not, the card reads "Testing {Agent} · round {n}" and lists "Changes so far" above the questions; otherwise it reads "Tested {Agent} · {n} questions", with " · {m} rounds" when `round` is set, and lists "What changed, in order" after them. Its subtitle is the Agent's @handle, the summary, and how many changes were saved. A row per question shows the verdict as a chip and its earlier verdicts as the model wrote them, or "was: {before}" in a report without `round`, a single round against the first; each opens in place to the question and the whole answer as Slack shows them. A gone row reads "A question asked over an hour ago" and opens to nothing. A change's row shows its `effect` and opens to its `why`; it shows no old and new wording. Then the next line. A client that draws no card hears to tell the person one line a round while testing goes on, and to give the results with the last report. The card calls no tool, tells the host's model nothing and keeps nothing.

With `continues: true`, a proposal or setup link's card sends one fixed sentence in the chat, as the person, through `ui/message` once the press it waits for succeeds: "I created {Agent}. Carry on." once a Create's Agent arrives in Slack (ready, or needing attention), "I saved the change to {Agent}. Carry on." once a Save applies (after its confirmation, when it needs one), and "{Service} is connected to {Agent}. Carry on." (or "is signed in again for") once a sign-in the card followed finishes. The model reads the message as the person's own words, so each name in it is quoted as JSON quotes it, on one line, cut at 60 characters: a member-chosen name reads as a name, never as an instruction. Cancel, Keep and Undo send nothing, and neither does any card without the flag. A card sends at most one such message: its widget state keeps `continued` beside its outcome, written before the message goes, so a card that mounts again in a reopened chat never sends it again, and the host's refusal of it shows no error, since the press it followed did what it should (`carryOn` in `src/mcp-cards/card-model.ts`). `reason` on `propose_agent_change` shows on the change card as "Why: …", because a card sits above the model's text in a ChatGPT turn. `propose_agent`'s card names the workspace before the press ("In {workspace}'s Slack"), and its issues say when another Agent already got no handle because Slack needs a paid plan. `get_creation_status` says `paidPlanNeeded` for that case, where the Agent still answers its creator in direct messages from Chickpea's Home tab, and the card leads with that.

The MCP door has none of the Slack door's tools, such as `propose_workspace_changes` and `apply_workspace_changes`; Chickpea in Slack keeps them. Tool annotations mark reads with `readOnlyHint: true`. The 5.0 tools state all their hints under OpenAI's rule, so an overwrite, removal or irreversible send is `destructiveHint: true` whether or not undo reverses it. `cancel_setup_link` and `disconnect_app` say `idempotentHint: true`: a repeat returns `setup_link_unusable` or `not_found` and has no second effect. The welcome an Agent posts in a public Channel it joins is such a send, so `add_agent_to_channel` and `create_agent` are destructive; a hint is per tool, so `create_agent` is destructive even when a call names no Channel, which keeps `propose_agent`'s `create.arguments` one call. Each 5.0 tool declares `securitySchemes` and an `outputSchema`. The server checks every result strictly, so a field the contract does not name never leaves, but the listed schema carries no `additionalProperties: false` anywhere (`openOutputSchema` in `src/management/mcp-v5/conventions.ts`): a client that checks results against the listing it kept, as the MCP SDK client does, still accepts a result once a release adds a field. Input schemas stay strict. Each 5.0 tool returns only the IDs a later call takes, such as `agentId`, and no revision numbers (an opaque `version` stands in for one), and fails with one shape, `structuredContent.error` with `code`, `message` and `retryable`. Each 5.0 write sends one operation, or a fixed pair, through `applyWorkspaceChanges`, so `policy.ts` decides what waits for confirmation exactly where Admin asks "Are you sure?". Such a write returns `needs_confirmation` with a `confirmToken`, a Markdown preview and an absolute `expiresAt`; `confirm_change` applies exactly that change. The Markdown preview, like the Slack door's change-set preview in `presentation.markdown`, backslash-escapes CommonMark syntax in stored text (`` \ ` * _ [ ] < > # | ~ ``), so an Agent name cannot add a link, image, emphasis or HTML, and control and line-separator characters become spaces, so it cannot add a line. The token is the change-set proposal's ID, and the proposal's `confirmation_expires_at`, a nullable column added for this, is set 30 minutes out for 5.0 calls only; Slack sets leave it NULL and never expire. Every 5.0 tool that can make a set passes the lifetime, `issueSetup`'s `request_setup` included, so an MCP set with it NULL was made by a 4.x tool. 5.0.0 removed the tool that confirmed it, so such a set reads as expired (`changeSetExpired` in `src/management/service.ts`): `confirm_change` refuses it with `confirmation_expired` and applies nothing, `get_confirmation` says `expired`, a replayed call shows no preview, and `decline_change` still retires it. The older `expires_at` column is not read: rows from before expiry was retired still hold values there. Confirm refuses a pending set past it with `confirmation_expired`; a completed set keeps replaying its result, and the startup reactivation of legacy `expired` rows is unchanged. An expired set stays pending until a newer one in the same scope marks it stale, and the retention sweep deletes it 30 days after that, as for any unanswered proposal. A write stores its request under an ID derived from the caller, the tool and the exact arguments, so a retry with the same `idempotencyKey` replays its result before any version is checked. An `undoToken` is the change's request ID. Over MCP it is bound like a `confirmToken`, to the person, membership and MCP app that made the change, and proposing a destructive reverse uses it up: a retry with the same `idempotencyKey` replays that confirmation, and any other undo with the token is refused, before or after the confirmation. Slack keeps its own semantics: the person's typed undo there, and a trusted connector undoing a Slack receipt, still reach the person's changes from another door, and in Slack a newer undo replaces a pending one. An undo record from before 4.4 is bound to its person only. `create_agent` with `channels` creates the Agent, then grants its Channels in a second request keyed off the first, because a creation's call carries no Channel reach. Without an `agentId`, `create_agent` derives one from the name; when an Agent the caller cannot see already holds it, the call tries the next free suffix, up to three IDs, each under its own derived request so a retry replays the same Agent. `update_agent` with fields and `imageModel` is likewise two requests, so the pair has no single undo. `propose_agent` and `propose_agent_change` save nothing. `explain_agent` shows an Agent as it would run for a person in a place, resolved through `resolveAgentRunPlan` without binding a model route or registering a credential use: its prompt parts, its tools by connection and why any are missing, its model and whether it can run, and a token estimate (pi-ai's, characters ÷ 3.5). `check_agent` checks each part and gives a fix for each failing one. It is the one 5.0 read with `openWorldHint: true`, because it tests the Agent's custom API and MCP connections with the one request each that the service's connection check sends; catalog connections get only their stored state, and admission is judged from stored configuration. Both show only what Admin shows the caller: a member never sees a private Channel Admin hides from them, and an Owner or Admin looking as another person sees that person's own accounts by service name, connected or not, with no label, connection ID or tool names.

The 4.5 writes follow the same path. `connect_service` and `reconnect_service` hand out a link and never take a key. For a catalog service they call `prepareConnectorSetup`, the method behind `prepare_connector_setup`, which reconnects an existing sign-in through `prepareConnectorReconnect`; the link is whatever that method returns for an MCP caller: the one-connection `/setup/` page with a `setupToken`, or Admin's page for a connector that page cannot serve. `reconnect_service` takes that path for a managed sign-in, and for a catalog connection whose sign-in was left unfinished or needs attention, which the service then finishes in that same connection. A ready catalog connection, or one the setup page cannot serve, gets its own sign-in link instead. `connect_service` refuses a service the Agent already has in that owner's lane and names `reconnect_service`, because a second link would sign the same connection in again. A custom API or MCP connection is added with `update_agent` under the call's key, and its key or sign-in gets a `request_setup` link; a stored result keeps no link, so every call, a retry included, gets a fresh one, and both tools say `idempotentHint: false`. Adding an open MCP server, or pointing one at a new URL, asks it for its tools, so `connect_service` and `update_connection` say `openWorldHint: true`. `update_connection` changes only custom connections, and a catalog MCP service's marks: for one, `changes` may hold only `readTools` and `writeTools`, and a call naming any other field is refused whole as `invalid_input`. A reviewed connector (Meta Ads, Bugsnag) is refused with a link to the Agent's page in Admin, where its tools are chosen, and a catalog API service is refused. A change to its hosts, paths, methods, key header or value prefix, or an MCP server's URL, is a change to the credential policy, so the service deletes the saved key in the same call and the connection waits for it again; the result carries the link, and the description tells the model to warn the person first. `readTools` and `writeTools` mark a custom or catalog MCP server's allowed tools as reads or writes, the `toolPolicies` that Admin's API (`PUT …/mcp/tools`) and the Slack door's `update_agent` operation write, through the same `update_agent` write and the same check that the caller may change that connection: an Owner or Admin for a team connection, its owner for a personal one. A tool not named keeps its mark and its argument limits while it stays allowed, and only an allowed tool can be marked. A tool whose server said `readOnlyHint: false` at its last discovery is never marked as a read: `update_connection` refuses it as `invalid_input` and writes nothing. The Slack door's `update_agent` and Admin's API store marks without that check, so `mcpToolDeclaredRead` also counts no such mark as a read, wherever it was set: when a practice run's plan is compiled and again on every call, so a marked tool stops being a read at the next check after a discovery stores `readOnlyHint: false` for it. Chickpea asks a server for its tools only when the connection is created, its key is set up, or it is signed in or reconnected, never during a run, so the hint is as old as the last of those. A tool the server adds later has no mark, so it is not a read until someone marks it. The `readTools` description tells the model to mark a tool as a read only when the person confirms it only reads, never from its name alone. A tool its server says changes things (`readOnlyHint: false`) can't be marked as a read: `update_connection` refuses it as `invalid_input`. A mark goes with its tool's allowance, and an argument limit stays with its tool: a tool that `update_connection` or Admin's tool editor dis-allows or allows again loses its mark, however it was dis-allowed, and the Slack door's `update_agent` stores a mark only for a tool it allows. The creation stores it beside the Agent, outside its configuration: no edit, revision, recipe or archive changes it, and an Agent created without one, or before Chickpea kept it, has none. `prepare_connector_setup` is the credential-safe connector entry point in Slack, and its service method is the one `connect_service` and `reconnect_service` call over MCP. Give it an editable Agent plus a connector catalog id or display name (for example `gmail` or `Gmail`). On both doors it returns a setup link (`/setup/<setupOperationId>`) to a page for that one connection, locked to that Agent. The link expires after 24 hours and finishes once, and a human completes consent there. A Slack link is for anyone in the thread who can edit the Agent. An MCP link opens only for the person whose client asked for it; anyone else gets the unavailable page. When the page cannot set up the connector (a catalog entry it does not serve, such as an API connector that signs in with OAuth), the tool returns the Agent's Admin page instead, with no `setupOperationId`. A finished MCP link wakes no Agent: `get_setup_status` reports it `completed`, the page tells the person to go back to the app that sent them, and Chickpea DMs them a one-line receipt. The page names the app only from Chickpea's own list (ChatGPT by its exact client ID; Claude, Claude Code, Codex, Cursor, VS Code, Gemini CLI, Zed and Goose by client ID or registered name) and otherwise says "your app", so an app's self-chosen name never appears in Chickpea's words. The tool refuses with `setup_unavailable` before writing any link when the organization has no Slack workspace, with `links.admin` pointing at Admin to connect Slack, and when the deployment has not configured a managed connector's sign-in, with `links.admin` pointing at Connectors in Admin Settings. The resulting connection belongs only to that Agent; another Agent must start a separate setup even when it will authorize the same external account. In a Slack conversation routed through a specific Agent handle, the adapter supplies that current Agent as the default target; credentials must never be requested in Slack or model context.

`connect_model_provider` is the same shape for a workspace model provider API key (`anthropic`, `openai`, or `openrouter`), on the MCP door only, through the service's `prepareProviderSetup`; Chickpea in Slack keeps using a `request_setup` operation with a `provider_credential` target, which goes through the normal proposal when it replaces a stored key. The tool issues the identical 24-hour setup record (`src/management/service.ts` `prepareProviderSetup` → `issueSetupRecord`, the record `request_setup` would create) without a proposal round trip: an authenticated MCP call is already the typed command, and the handoff page is where the person acts. Unlike a connector link, the page is bound to the requester: exchange and completion require the same signed-in person (`principalMatchesSetup`) with live `admin.configure`, so a colleague cannot finish it. The result carries `provider`, `replacement`, `handoffUrl`, `setupOperationId`, `expiresAt`, and `links.admin`; the key itself is typed on the setup page, validated against the provider, and stored by `src/management/setup-routes.ts` `completeFormAction`, so it never appears in a tool argument, tool result, receipt, or `get_setup_status` read. `cancel_setup_link` works on these links like any other. GitHub App setup, the coding sandbox, the Composio key, and Agent avatars have no MCP handoff: GitHub is a GitHub-hosted App manifest flow with a CSRF state minted by an Admin session, not a paste-a-secret form, and the others are Admin-only settings. `tests/management-provider-handoff.test.ts` covers the tool end to end, including the browser completion and the no-secret-in-any-result assertion.

Receipts and errors that name something only Admin can change carry `links.admin` to the exact Settings section (`src/management/admin-links.ts`): every `request_setup` outcome for a provider key and every `remove_provider_credential` outcome, whatever its disposition (`setup_required`, `confirmation_required` when a removal waits for confirmation or Slack holds a stored-key replacement for approval, a member's `operational_access_required` denial, skipped, failed), plus the `invalid_request` errors for a deployment-provided or missing provider key, point at `/admin/settings/providers`, as does every `set_workspace_model` outcome; every `update_member` outcome points at `/admin/team`. The top-level `links` on a receipt stay the first changed Agent's; a Settings link is the top-level fallback only when no Agent changed. Like the Agent links, these are added at return time, need a usable deployment origin (no bare paths), and are stripped before persistence, so `get_operation` returns the stored receipt without them.

`import_skill` accepts a public GitHub repository, direct GitHub tree URL, skills.sh link, or `owner/repo` reference that appears in the authenticated current Slack request. A direct skill-directory URL is preferred because the service inspects one directory and pins its commit before fetching `SKILL.md`. A source with multiple candidates returns bounded names, descriptions, and immutable source URLs without changing configuration; the requester posts the chosen `sourceUrl` in a new message before the next call. A new bounded scriptless skill installs immediately and returns a Slack-ready receipt plus an undoable operation ID. Different same-name content returns `replacement_confirmation_required` with the exact clarification text required before a new-message retry with `replaceExisting: true`. Packaged scripts are rejected because Chickpea inline skills cannot execute imported files. Over MCP, `import_skill_from_github` takes the same path and requires `agentId`. An authenticated MCP call is already the person's typed command, so it installs immediately. A same-name skill with different content is replaced only when the call sets `replaceExisting: true`, which the client sends only if the person wants it replaced; the Slack replacement phrase does not apply.

`upload_skill_files` (over MCP) installs skills from files the person has, through the reader Admin's Skills upload uses (`resolveUploadedSkills` in `src/config/skill-upload.ts`). Each file is `{ name, text }` for a `SKILL.md` or other markdown file, or `{ name, base64 }` for a `.zip` or `.skill` archive. Every skill found is upserted by name and every other skill on the Agent is kept: a new name is `added`, the same description and instructions are `unchanged`, and different content under an existing name is a `conflict` left as it is unless the call sets `replaceExisting: true`, which makes it `replaced`. Files that are not skills, or that fail a bound, come back in `issues`. Only instructions are installed; scripts and other package files are listed as omitted. A change applies at once through the same authorization, revision, undo and audit path as `import_skill` and returns an undoable operation ID plus `links.admin`. Nothing is stored beyond that operation: a retry with the same key and files replans them against the skills the undo record saved and returns the same receipt. Tool arguments are model output, so a model that copies text sends one or a few files per call, and `chickpea-cli skills upload` sends archives and many files from disk with no model in the path. The 1 MiB MCP request cap and the 1 MiB management request cap still apply. Both doors digest each file as its name and SHA-256 for the operation ID.

In Slack, `upload_skills` takes no file content and no file IDs. It mounts only on a turn whose message carries files, and the service reads exactly the files the host listed for the person's current message (`attachmentFileIds` on the Slack origin, never stored), one at a time within one 8 MiB budget, through the installation's attachment client with `accept: ['text_original', 'zip_original']`. It refuses a turn another Agent's ask started and a message that also addresses someone else. New skills install at once. A same-name skill with different content is replaced only when the person's own addressed message asks to replace it: one host side call on the routed Agent's model sees only that message and the names of the skills it would replace, never file contents or thread history (`classifySkillReplacement` in `src/slack/interaction-intent.ts`). A no, a failure or a timeout leaves those skills unchanged, lists them as conflicts, and the receipt says to send the files again with a request to replace them. Each message and target Agent is judged at most once: an unchanged outcome is recorded too, so a retry in the turn replays it, and the call's usage is metered against the Slack turn as the typed-approval judge's is. A Slack call that passes `files` or `replaceExisting` is refused. The key is scoped to the Slack event, so a retry in the turn replays its receipt and a later message with the same files reports them unchanged. A file Slack cannot give becomes a left-out issue at `Attachment N`: not a skill file, not a zip, over the budget, unreadable, or an older shared gateway that refuses `accept` (`gateway_attachment_unsupported`, which points the person to Admin upload). Deploy the gateway before a Core release that sends `accept`.

`manage_agent_skill` changes one named installed skill with `enable`, `disable`, or `remove`. The service reads the current Agent, verifies the requester, preserves every other skill, and writes an idempotent reversible change. Slack calls must match the exact authenticated current command; over MCP, `set_agent_skill` takes the same path, and an authenticated call is already the exact typed command. Chickpea connectors are trusted integrations, so connector identity never adds an approval gate. A clear single-skill command applies immediately and returns a Slack-ready receipt plus undo. Questions, negated commands, ambiguous targets, generated content, and compound edits do not qualify for this path. The generic proposal tool rejects an exact qualifying single-skill command so a model cannot turn it into an unnecessary approval round trip.

On the Slack door, `propose_workspace_changes` accepts exact typed consequential edits and writes no configuration. It rejects Agent creation. Each call must include a requester-chosen `idempotencyKey`, the current guide version, and an `authoringReason` (`agent_creation`, `agent_edit`, `skill_creation`, `skill_edit`, or `onboarding`). Retrying the same bound key and exact operation digest returns the original proposal; reusing it for different content fails closed. `apply_workspace_changes` creates one sufficiently understood base Agent immediately when the request contains exactly one `create_agent` operation. A call that creates Agents may also hold `update_agent` and `request_setup` items, which is how a recipe configures the Agents it creates; Channel reach, schedules, and other changes wait for a later call. An `update_agent` with `expectedRevision: 0` targets the Agent that a `create_agent` earlier in the same call creates, at the revision the call left it, and must list that creation in `dependsOn`. It routes every operation whose door posture is confirmation into a frozen change set instead of bypassing review: in Slack that follows Slack's approval policy, and over MCP only the destructive set. Apply requests accept at most 25 ordered operations. `dependsOn` gives a progressive batch explicit prerequisites; a failed prerequisite skips only its dependents. A progressive apply batch is not globally atomic, and every item returns its own durable disposition.

## Connect a coding agent

Every deployment serves two public, unauthenticated connect routes from `src/management/connect-routes.ts`: `GET /connect.md` is a guide written for the coding agent with this deployment's real URLs substituted in (detect the client, hand an agent inside the Claude app a pre-filled Add custom connector link for the person to confirm, otherwise write its configuration from a table covering Claude Code, Codex, Cursor, VS Code, Windsurf, Gemini CLI, and a generic JSON block, run the client's sign-in, hand off to a new session or thread with Tested pending if the client loads servers only when one starts, prove the connection with one `inspect_workspace` call reported as three separate lines, then find the first teammate through the discovery guide), and `GET /connect` is the page a person opens to copy the one-line prompt `Connect my coding agent to my Chickpea using https://<origin>/connect.md` plus an Add to Claude link and the direct Claude Code and Codex commands. Both work before Slack setup is finished and say that `/mcp` answers 404 until then. They contain nothing secret and no internal identifiers, so they are cacheable for a few minutes. `tests/connect-routes.test.ts` covers headers, origin substitution, and the client list; `scripts/verify-cf-smoke.mjs` fetches both routes on the Worker. Signed-in people get the same table inside the product: Admin Settings → Coding agents (`/admin/settings/agents-clients`) renders it from `GET /admin/api/mcp-clients`, which every authenticated principal including a member may read, and which serves the identical snippets from `src/management/mcp-client-config.ts` plus the hosted Claude app and ChatGPT entries and the Claude, Cursor, and VS Code one-click install links.

The agent-run install guides make this a required step: `INSTALL_CHICKPEA_CLOUDFLARE.md` step 8 and the `INSTALL_CHICKPEA_NODE.md` section "Connect this coding agent" have the installing agent add the new deployment's `/mcp` server to its own client, start that client's sign-in, call `inspect_workspace`, and report configured, signed in, and tested as three separate lines before it hands over. They fetch `/connect.md` and follow its steps 1 to 5 (the install guide owns the first teammate), and carry an inline client table for releases that predate the connect route (up to and including v0.1.22), which `tests/install-guides-connect.test.ts` keeps byte-aligned with `CONNECT_CLIENTS`.

Add a remote/custom MCP server in the client and use the exact Chickpea deployment URL ending in `/mcp`. Do not create or paste a bearer token. A compatible client discovers OAuth metadata, registers as a public PKCE client when needed, opens Slack sign-in and Chickpea consent, then reconnects with a resource-bound access token.

Use one authorization tab and keep the initiating command running until it
reports a result. `codex mcp add` can start OAuth itself; run `codex mcp login`
only if sign-in is still needed after `add` finishes. Codex both opens the
browser and prints the authorization URL, and a coding agent's shell tool shows
that output to the model. The URL is single-use: `/connect.md` tells the agent
not to show it to the person unless the command prints "Browser launch failed",
and to wait for "Successfully logged in" before it reports anything.

The MCP client owns its loopback callback page. Codex 0.154.0 responds to the
first callback with a completion message and then closes the listener after
the login finishes. See its [callback handler](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/rmcp-client/src/perform_oauth_login.rs#L262-L310)
and [automatic login during add](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/cli/src/mcp_cmd.rs#L490-L523).
A later consent click in a duplicate tab or a callback revisit can therefore
show connection refused at `127.0.0.1` or `localhost`. This is distinct from a
404 at Chickpea's `/mcp` endpoint before Slack setup finishes.

Check the client's result before retrying. If it reports success, close the
leftover tab and verify with `get_account`. If login failed or timed
out, preserve the first error and retry once using a fresh login URL. Keep
working credentials. If the first callback fails while the command is still
waiting, investigate the client's listener and browser restrictions separately;
the duplicate-tab explanation is not established in that case. Chickpea must
return the exact registered callback, and cannot replace it with a success page
before the client exchanges the authorization code.

`ERR_BLOCKED_BY_CLIENT` is a separate browser-side failure. It can appear even
when the client receives the callback and completes authentication. Check the
client's result and the read-only MCP call before treating the connection as
failed. Compare with a direct callback in an isolated local fixture before
attributing the block to Chickpea's consent handoff; do not relax OAuth or
browser protections to hide the error.

Authorization should show one permission: manage this Chickpea workspace. For a client registered for renewal, it also says the agent stays signed in. Slack OIDC proves the person, while Chickpea independently requires the exact active workspace binding and membership on every MCP request. Disconnect or revoke the MCP connection from the client when it should no longer hold a refresh token, or revoke it from any connected coding agent, as described under [Connected MCP clients](#connected-mcp-clients). Suspending or removing the Chickpea member immediately blocks live MCP requests without waiting for client cleanup, and it revokes their MCP grants and Admin sessions, whether the change came from Admin, Slack, or MCP. A role change ends only their sessions, because every MCP request rereads the role. A suspension or removal revokes before the membership changes and again after it, because a client can refresh its token in between. A revoke that fails before the write leaves the membership unchanged; one that fails after it reports the change failed, and asking again finishes the sign-out.

### Connected MCP clients

`list_connected_apps` lists the signed-in person's own MCP clients: each one's `appId` (its OAuth client ID), the `name` it registered with, when the person first allowed it (`connected`), when it last signed in or renewed its access (`lastActive`, which an active client renews every 15 minutes; absent when it holds no token), and `thisApp` for the client making the call. The list comes from the person's Better Auth consents and tokens (`listOAuthClientsForUser` in each backend, through the service's `listMcpClients`), so it never shows anyone else's client and never returns a token. `disconnect_app` takes one `appId` from that list and applies at once: it deletes the person's consent, refresh tokens, and stored access tokens for that client together (`revokeOAuthClientForUser`), and leaves the client's registration and other people's grants alone. The client can no longer renew; an access token it already holds keeps working until it expires, up to 15 minutes. Disconnecting the current client is allowed, and the reply says it must sign in to Chickpea again. An `appId` the person has no grant for, another person's included, fails with `not_found` and the same message as one that does not exist. Slack cannot call either one. The backend contract (`tests/helpers/better-auth-backend-contract.ts`) proves on SQLite, D1, and PostgreSQL that the revoked client's refresh fails while the person's other clients and other people's still refresh.

Admin's Settings → Connected apps (`/admin/settings/connected-apps`, `src/admin/connected-apps-api.ts`) is the same list and revoke for the signed-in person, through the same service methods with an Admin origin. Every member can open it. It shows each app's name, when it connected and when it was last active, and asks in the row before it disconnects. A known app is named in Chickpea's words; any other name is marked as provided by the app, as on the consent page. A personal token cannot use it, and Admin's gate checks the origin of the disconnect as it does for every Admin write. `list_connected_apps` and `disconnect_app` return the page as `adminUrl`, and the consent and Already connected pages link to it. `tests/admin-connected-apps-route.test.ts` covers the routes.

Dynamic Client Registration is an intentionally bounded compatibility window for current clients. It accepts public clients only and validates exact loopback or HTTPS redirects. The deployment's durable limiter allows 20 registrations per source and 1,000 in total per 15 minutes; a hosted host supplies its own per-source limit, which Core calls before every registration. About 1,000 registrations that no one has consented to are kept. The cap is approximate under a concurrent burst: requests that arrive together each count before the others register, so more than 1,000 can briefly remain, and refusal applies once a request sees the count at the cap. Past the cap, the oldest one older than 15 minutes makes room for the new one. A registration younger than 15 minutes is never evicted, so a flood cannot cancel a sign-in in progress; when the cap is full of registrations that young, registration answers 429 `registration_quota_exceeded` until the oldest turns 15 minutes old. A registration that no one consents to within 30 days is pruned. A client someone consented to is never pruned. A client that kept a pruned registration cannot sign in. Better Auth redirects its browser to `/api/auth/error?error=invalid_client`, which is not a public route, so the person sees a bare "Not Found" page. To recover, clear this server's stored authentication in the client, then connect again so it registers anew. Do not enable confidential client metadata or widen redirect rules.

Self-hosted deployments use dynamic registration only. Chickpea Cloud also accepts a client ID metadata document from any public client, or from a client that signs its token requests with keys on its own origin. [Coding-agent MCP authorization](../authentication.md#coding-agent-mcp-authorization) lists the protections and the remaining risks. An app that signs in by its document does not register, and all users of one app share its one stored client. That client must meet the rules a registered client meets: public, or `private_key_jwt` with keys on its own origin, with exact HTTPS or loopback redirects. Each HTTPS redirect must also be on the client ID's host or a subdomain of it. Its first sign-in counts toward the same per-source limit and pending cap. Until someone consents to it, each later lookup counts toward the per-source limit too, at authorize and on the consent page, so a person's first sign-in to a new app counts about three times. VS Code and Zed publish their documents uncacheable, so Chickpea fetches them again at every authorization, consent, token exchange, and refresh. The plugin allows 30 fetches per document host and 120 in all per minute in each isolate. Past that, it answers 429 `temporarily_unavailable`, except to a person who consented to the client, for whom the stored client stands in for an hour after its document last answered. When the host cannot be reached, the stored client stands in for up to a day. The consent page adds a Domain row with the host that serves the document, such as `claude.ai`, which the document cannot change. Every sign-in by a document client asks for consent, even after an earlier approval, because its client ID is public and its redirect does not prove which app asked. Any local app can listen on a loopback port. A document that declares a native app signs in only on loopback, because in practice a desktop app's HTTPS redirect relays the code onward: `https://vscode.dev/redirect` forwards it to the address in the request's state, which may be a codespace's host on github.dev. A request with `prompt=none` gets an error, not a code. A client ID that is not an HTTPS URL on a public DNS name is an unknown client, and Chickpea fetches nothing for it. The published documents of Claude, Claude Code, Codex, VS Code, Zed, and Goose pass these rules. ChatGPT's `private_key_jwt` document is accepted. Cursor's lists a redirect on `grok.com`, so Chickpea Cloud refuses it. Hosted shared auth advertises `none` and `private_key_jwt`; a dynamically registered client that picks `private_key_jwt` is refused at registration, as one that picks `client_secret_*` is. Self-hosted deployments keep the gate. Before one trusts remote metadata, the Worker implementation must safely resolve DNS, reject special addresses, pin the resolved address through TLS, and refuse redirects.

## CLI

`chickpea-cli` (npm, source at `packages/cli`) is a scripted client for this surface. `npx chickpea-cli doctor <origin>` runs the unauthenticated half of `scripts/verify-management-mcp.mjs` against a public origin: protected-resource metadata, authorization-server metadata, JWKS, and the 401 challenge, and explains a 404 as unfinished setup. `chickpea-cli mcp config <origin>` prints the client snippets for Claude Code, Codex, and Cursor. `chickpea-cli login <origin>` performs the public PKCE flow described above through the `@modelcontextprotocol/client` SDK and stores the tokens under `~/.config/chickpea` (mode 0600), keyed by origin. `logout` revokes the refresh token at `/api/auth/oauth2/revoke`. The resource server verifies an access token by signature and expiry, so the one already issued keeps working against `/mcp` until it expires, up to 15 minutes. Suspending or removing the member blocks the session at once. From 0.3.0 the built-in commands call 5.0 tools and refuse a Core without them (`UPDATE_REQUIRED`): `workspace inspect` calls `get_workspace` and every page of `list_agents` (at most 50; `--include-archived` lists archived Agents on a Core that leaves them out), `recipe export` calls `export_agents`, and `recipe preview` is removed. `tools list` and `call <tool>` reach any tool, and `call` prints a normalized `{ ok, result | error }` envelope for 5.0 results and 4.x envelopes alike. `skills upload <origin> <agentId> <file...> [--replace]` reads `.md`, `.markdown`, `.zip` and `.skill` files from disk and calls `upload_skill_files`, batching the files so each call stays under the 1 MiB MCP request cap. It refuses a single file over that cap and points at Admin's Skills upload instead.

The CLI follows this runbook's confirmation model: a destructive change waiting for confirmation is printed with the exact `confirm_change` command and its `confirmToken` and is never confirmed automatically, and a setup link is printed with the 24-hour, anyone-who-holds-it warning. It never accepts a token, provider key, or Slack credential as an argument or environment variable. Package README: `packages/cli/README.md`.

## Roles and confirmation

| Actor | Inspect workspace | Operational changes | Members | Normal Channel work |
|---|---:|---:|---:|---:|
| Owner | Yes | Yes | Yes | Yes, when a Channel allows it |
| Admin | Yes, with the team list | Yes | No | Yes, when a Channel allows it |
| Member | Editable Agents only | Create and edit permitted Agents | No | Yes, with live Slack membership proof |
| Unbound Slack participant | No | No | No | Only ordinary assigned-Channel interaction |

Slack workspace roles are not Chickpea roles. Every call re-resolves the live Chickpea membership and access overlay. Tool arguments cannot select a user, organization, membership, Slack requester, or credential scope.

The adapter also supplies the acting scope; model-authored arguments cannot forge it:

| Surface | Authoring scope |
|---|---|
| User Agent in Slack | Its own complete configuration only, when the requester may edit it |
| Base Chickpea Agent in Slack | Create Agents and edit requester-permitted Agents |
| External MCP client | Requester-permitted Agents, with no implied acting Agent |

A user Agent may self-manage instructions, skills, model, presence, edit policy, connections, repositories, memory, reach, setup, routines, and lifecycle. Existing setup, membership, revision, Channel, destructive-confirmation, and audit gates still apply. Cross-Agent or workspace-authority work returns a bounded Chickpea handoff or a permission-safe denial without exposing the target configuration. An archived Agent cannot process another Slack turn; restoration must enter through an active authorized surface.

The request itself is approval only when the trusted service derives the exact command from the authenticated current message and proves it authorized, reversible, local-only, and free of authority, reach, credential, capability, or third-party effects. Today that includes one explicit enable, disable, or removal of a named existing skill, the purpose-built exact GitHub import and undo tools, and a change to one Agent field on its own: instructions, model, effort, image model, name, description, requested Slack handle, or turning the Agent on. Saving or forgetting Agent memory also applies at once and can be undone. New or generated skill content, inferred changes, compound changes, destructive actions, external consequential writes, capability expansion, and reach or authority changes use `propose_workspace_changes`. Ambiguous targets or replacements need clarification, not a generic approval prompt. The returned preview is the single approval boundary when confirmation is required: never ask for permission before proposing and never ask for another approval after the requester accepts that preview. The apply tool still returns a bound proposal for any operation whose policy requires confirmation, including:

- deleting an Agent or a routine;
- changing member authority;
- removing or replacing credentials;
- expanding capability scope;
- disabling an Agent that is published to a Channel; or
- archiving or restoring an Agent, or granting or revoking Channel reach;
- changing a Workspace model (Slack only; Admin and MCP apply it directly); or
- overwriting an existing Agent from a recipe.

### Approval in Slack

In Slack, only the person approves. The host applies a change set when the requester presses its Approve button or replies that they approve it, and the Agent has no tool that applies one. An exact approval such as `approve` applies at once. Other wording is judged only when it answers the set: the turn that proposed it is still the Agent's latest in that thread or DM, so the Agent has asked nothing since. Then one side call on the Agent's model reads the requester's message and a summary the host builds from fixed labels (`approvalChangeSummary`), never the set's content, and answers approve, decline, or other (`classifySlackManagementApproval` in `src/slack/interaction-intent.ts`). Approve applies the set as `approve` does. Decline retires it, as the Cancel button does. Either retires only a set that still waits: one an approval claimed first goes ahead, and the Cancel button's card then says it was already approved. Other, a failed call, or a timeout applies nothing, and the message reaches the Agent as conversation. After the Agent takes another turn, only the button or an exact approval applies the set. When the person asks about the waiting change, the Agent answers and proposes the same operations again in that reply. The host keeps the pending set, with its card, and records the answering turn as the one that proposed it, so a plain "ok, go ahead" after the answer is judged. The same holds when a replayed call shows the set again. The host cannot see a question the Agent asks in the same message as the preview, so the Agent is told to end that message with the approval request and ask nothing else until the person answers, and the judge answers other for a reply that also answers anything else. Nobody else's message is judged, and neither is an Agent's ask, a click, a reaction, or a stop phrase or check-in such as "cancel that", which keeps its steering meaning. On a turn another Agent's ask started, every change waits for that approval, including a change that would otherwise apply at once. A setup request after a held change in the same call waits too: the approval issues its one-time link and the receipt carries it. A setup request that would replace saved credentials cannot wait for approval in Slack, so the Agent refuses it and sends the person to Admin.

`npm run evaluate:slack-approval-intent` checks the judge offline: it validates `evals/slack-approval-intent/cases.json` and sends every case through the production side call to a stubbed provider. It does not measure judgment. `npm run evaluate:slack-approval-intent:live -- --model <provider/model>` judges the corpus with a real model and fails on any false approval, more than one false decline, approve recall under 0.9, decline recall under 0.75, or a failed call; its private report goes under `~/.chickpea/evals/slack-approval-intent/`.

### Confirmation over MCP

An MCP client acts with the signed-in person's Admin authority. Every change the policy allows for that person applies at once, through the 5.0 write for it. The exceptions are the changes the Admin UI asks "Are you sure?" about (`assets/admin-ui/admin.js`), plus Agent deletion, which the Admin UI has no button for:

| Change | Admin UI confirmation |
|---|---|
| `delete_agent` | No Admin UI; treated as destructive |
| `delete_routine` | Routine delete modal ("cannot be undone") |
| `update_member` that suspends or removes a member, or promotes or demotes an Owner | Team confirm modal; a Member and Admin role swap and a reactivation apply directly in both |
| `remove_provider_credential` | `prov-remove` then `prov-remove-confirm` |
| `update_agent` that removes an existing `mcpServers` or `apiConnections` entry, or `disconnect_connection` | "Disconnect account" confirm |
| `remove_website_login` | Website login "Remove" confirm |
| `update_agent` that disables an Agent with Channel grants | "Disable everywhere" callout |

In the service such an item returns `confirmation_required`, and the rest of the call waits in the same change set. A 5.0 write returns it as `needs_confirmation`, with `confirmation.preview` and a `confirmToken`, the change set's proposal id. The client shows the preview, asks the person, and calls `confirm_change` with the token after they agree. A destructive item that cannot share a change set with the rest of its call (a later `request_setup`, or a second change to the same object) fails with `confirmation_needs_own_call`; the rest of the call is handled without it, and the agent resends that item alone. Each MCP client keeps one pending change set per person. Another destructive change makes the earlier one stale, and confirming the earlier one returns `proposal_stale`. Removing a repository grant or a skill applies directly, as in Admin. `undo_change` applies directly unless its inverse is in this set, for example undoing an added MCP server. The posture comes from one table, `POSTURE` in `src/management/policy.ts`, keyed by policy reason and door; the Admin door's column is all immediate because the browser asks first.

An `idempotencyKey` is unique within one conversation of one requester: one MCP client, one Admin session, or one Slack DM or Channel thread, under the acting Agent (`managementIdempotencyScope` in `src/management/contracts.ts`). Retrying a key with the same operations in that conversation returns the first result, even when the workspace changed since; reusing it with different operations fails with `idempotency_conflict`. The same key from another client, door, or thread is a separate request. A key is a retry token, so send a new key for each new change: an MCP client that reuses `agent-research-v1` after deleting that Agent gets the first creation's receipt back and creates nothing. In Slack, `manage_agent_skill` and `import_skill` also scope the key to the requester's message, because models reuse keys such as `disable-unslop` in later turns.

Deleting an Agent needs it out of Slack first, on every door. An Agent with Channel grants, its own Slack app, or a Slack user group fails `delete_agent` with `invalid_request` and "Archive <name> first", until it is archived. Admin's `DELETE /admin/api/agents/:id` gives the same message with a 409 `agent_still_in_slack` (a Channel grant keeps its older `agent_still_referenced`). Archive ends the grants, retires the app, and completes only after Slack turns the user group off. Slack cannot delete a user group, so the archived Agent keeps the group's id for restore, and delete leaves that group off in Slack. Creation over MCP publishes the handle at once on a Slack plan with user groups, so such an Agent is archived before it is deleted. As in Admin, delete also waits while a Slack thread from the last 30 days still uses the Agent, and it removes the secrets of the Agent's own connections behind a cleanup marker a retry finishes.

A disabled Agent keeps its Channel grants and does not answer in them; enabling it again brings it back to the same Channels. A confirmed disable carries an undo, like any other one-change call: `undo_change` with the `undoToken` that either result returns turns the Agent back on.

The same live requester must confirm from the same MCP client or Slack conversation. An MCP confirmation expires after 30 minutes, and one a 4.x tool made before 5.0.0 reads as expired; a Slack proposal does not expire. A newer proposal from that same requester and origin supersedes the older pending one; in Slack, the same operations proposed again keep the pending one. `confirm_change` accepts only the `confirmToken` and applies the frozen operations; it cannot reinterpret them. A changed target revision, digest, permission, requester, acting Agent, or origin makes the whole change set stale or denied before its first write. Inspect again and present a newly calculated diff instead of retrying the old handle.

## Clean Agent creation

During exploration, keep the Agent design in the conversation and create no record. Once the base identity and purpose are sufficiently understood and the request reaches commit posture, call `apply_workspace_changes` immediately with that base creation by itself. Do not propose it and do not ask for a second confirmation:

```json
{
  "idempotencyKey": "agent-research-v1",
  "operations": [
    {
      "itemId": "agent",
      "kind": "create_agent",
      "clientRef": "research",
      "agent": {
        "id": "agent_research",
        "name": "Research",
        "description": "Synthesizes research for the team.",
        "requestedHandle": "research",
        "editPolicy": "all_workspace_members",
        "instructions": "Synthesize evidence and cite sources.",
        "enabled": true,
        "model": "openai/gpt-5.6-terra",
        "skills": [],
        "mcpServers": [],
        "apiConnections": [],
        "repositories": []
      }
    }
  ]
}
```

The base Agent is active immediately. A trusted Slack Channel request derives only that exact source-Channel grant; a DM and MCP request derive no Channel reach. It must not silently add a connector, repository grant, other Channel grant, or routine. In Slack, explicitly requested connector names can become up to three independently authorized `Connect X` actions in the welcome; they never ride inside the create operation or grant access. If Slack-handle or source-Channel publication fails, the Agent remains created and Chickpea reports the incomplete portion once. Handle a compound request by creating the base first, then sending each follow-on operation through its existing policy and confirmation boundary.

Over MCP, `create_agent` makes the same base Agent in one call. In Slack, `editPolicy: all_workspace_members` waits for approval.

The adapter, not the model, supplies requester authority. The acting membership is recorded as the Agent creator; tool arguments cannot forge it. Use current IDs and revisions returned by inspection rather than guessing them. Channel publication remains a separate operation, which Slack holds for approval and MCP applies directly: `put_channel` records the Slack Channel and `grant_agent_channel` performs live Slack membership, bot-membership, and Agent-presence reconciliation before activating the additive grant. A grant for an Agent that is off is refused at every door, before any proposal or Slack work, with `agent_off`; turning the Agent on is its own change, and neither a Channel add nor a Slack sync turns an Agent on. In Slack, `revoke_agent_channel` also rechecks that the acting member is in the Channel before removing reach. Over MCP, as in Admin, editor rights are enough. A `put_channel` that turns Chickpea off in a Channel (`lifecycle: archived`), or changes a Channel where it is off, turning it back on included, needs an Owner or Admin at every door. A member's refusal says so. Admin has no control for either move.

Successful configuration is active on the next newly admitted Slack event, including a reply in an existing thread. An already admitted response and all of its retries keep their frozen runtime plan.

## Connectors, repositories, and model credentials

Declare non-secret policy in the Agent operation: display name, approved MCP tools, allowed API hosts/paths/methods, OAuth scopes, or exact repository name. Never place an API key, OAuth code, bearer value, private key, authorization header value, repository installation credential, or secret-bearing URL in a tool argument.

An Agent's `mcpServers` and `apiConnections` are the connection accounts Admin lists under "In this Agent": team accounts and the requester's own. A management write creates, updates, and disconnects those accounts through Admin's connection account service, so Admin shows and removes them and the runtime uses them once they are ready. An Admin or Owner adds a team connection; a Member adds a personal one only they can use, as in Admin. A connection's `id` is its provider id, or its account id when two connections share a provider id; a new connection takes a short id (lowercase letters, digits, `-` or `_`) that becomes its provider id. A connection stores one credential: a bearer token, an OAuth sign-in, or, with `authMode: "none"`, the value of at most one header. Admin has no off switch for a connection, so `enabled: false` is refused; remove the connection or use `disconnect_connection` to stop the Agent using it. A reviewed connector (Meta Ads, Bugsnag) can be renamed, and a write may leave out its `toolPolicies`, but its tools change only through Admin's review. Every write also passes the rules Admin applies (`src/config/agent-write-rules.ts`): skill names and content, MCP and API URL checks, overlapping or duplicate API connections, the GitHub host, reviewed connectors such as Meta Ads and Bugsnag, which are added in Admin, and the hosted repository-grant mapping.

`inspect_workspace` also says who is asking and where. `slackTeamId` is the Slack workspace's team ID, which `inspect_routines` takes as `workspaceId`. `slackTeamName` is the workspace's stored name (the `slack.teamName` setting, read by `readStoredSlackTeamInfo`), the name Admin shows. It is left out when the installation's connected Slack credential belongs to another team, and a gateway install, which keeps no connected credential, still gets it. It is absent until Admin asks Slack for it, during onboarding or on the Slack connection card, and inspection never asks Slack for it. `caller` gives the signed-in person's `membershipId`, `role`, and `displayName`. `team` lists the members with their role and status for everyone Admin shows the Team page, Owners and Admins, and is absent for a Member; it carries no email. For each Agent, `groupDms` is `eligible` when the Agent answers in Slack group DMs, which only an Agent every workspace member may use does (at least one active grant in a public Channel its bot is in, the rule in `resolveTurnAgentAccess`); `not_eligible` otherwise, including a disabled or archived Agent; and `unknown` when Slack could not confirm its Channels. Inspection reads each granted Channel from Slack once; an Agent with its own Slack app is read with that app's bot, as Admin does. `ownSlackApp` is present, with the app's `handle`, while the Agent answers as its own Slack app. These fields are read-only.

`inspect_workspace` returns each Agent's `skills`, `mcpServers`, `apiConnections`, and `repositories` in the exact shape `update_agent` accepts, so a client can read them, change a field, and send the arrays back unchanged. A connection carries only the fields a client sets (`MCP_CLIENT_FIELDS` and `API_CLIENT_FIELDS` in `src/management/agent-connections.ts`). The server owns the rest: the credential namespace and header policy, status, discovered tools and their schema fingerprints, review mode, and the provider-reported account. The write schemas refuse those fields, and the service ignores them from any other caller. Each Agent's read-only `connectionStatus` reports the state: `lifecycleStatus`, `statusText`, discovered tool names, the provider account, and the last check.

On every write the service matches each connection by `id` and keeps the stored review mode and header policy. While the credential policy is unchanged (URL, transport, auth mode, header names, OAuth scope, preset, and header policy), it also keeps the secret, the status, and the discovered tools, so renaming a connection or changing its approved tools never drops a credential. A new connection, or one whose credential policy changed, starts unconfigured: an MCP server with no credential is `ready` once the check below passes, every other connection is `pending` until its setup link completes or a person enters its key in Admin, and its discovered tools start as its approved tools, so discovery can only narrow a non-empty approved list. An empty `allowedTools` counts as never discovered: outside review mode, the first discovery grants every tool the server offers.

An MCP server that needs no credential is checked when a management write adds it or changes its credential policy, as Admin's Test connection checks one before saving: the service lists the server's tools (`discoverMcpServer`, `src/management/discovery.ts`) and saves them as its discovered tools. A server that cannot be reached is not saved, and an `allowedTools` entry the server does not offer is refused with the tools it does offer. An empty `allowedTools` then allows every tool it offers. A tool choice on a ready MCP server names only its discovered tools, within the binding's ceiling, as Admin's tool editor requires; the change applies directly on both doors. `test_connection` stays read-only: it checks one saved API or MCP connection with its saved credential, sending an API connection one GET inside its own hosts and paths and listing an MCP connection's tools.

`save_connection_key` saves the key the person gave for one of an Agent's API connections that uses a key. It is a tool, not an operation, so the key never enters an operation record. It first sends one GET with the key to `path`, a required read endpoint inside the connection, as `test_connection` does. A 401 saves nothing and returns `key_rejected`. Only a 2xx saves the key, the way the setup page does, so the connection becomes `ready`, and the result reports the check. Any other answer saves nothing and returns `key_unconfirmed`: a 403 can mean an invalid key (Datadog and AWS API Gateway answer one), and many APIs give a 404 at a bare prefix whatever the key. Either refusal carries the setup link that `request_setup` would issue the person for that connection, so the model only relays it. When no link can be issued, the refusal tells the model to send one with `request_setup`. Over MCP it may replace a saved key. From Slack it saves only into a connection with no saved key, and only a key the requester typed in their own current message beside every host and path the connection sends it to, or a key they typed in the message that proposed this connection when they approved that change in the last 30 minutes, as `try_connection` admits it. With `authShape: "basic_username"` it saves the key as HTTP Basic credentials for a connection that sends `Authorization` with the prefix `Basic `, and refuses a key with a colon, which a Basic username cannot hold. The key is never returned. An MCP server's key goes through `request_setup`.

`try_connection` sends one GET with a key and saves nothing, so the model can find the host, auth header and endpoint that work before it saves a connection. It returns the check, whose `detail` is the service's own redacted answer, and `triesLeft`. In draft mode it takes a candidate `draft` (hosts, path prefixes, header, value prefix and `authShape`) and the key; `basic_username` sends the key as an HTTP Basic username, encoded host-side, and refuses a key with a colon. With `connectionId` and no key it tries that connection's saved key, and with a key it tries that key; a `draft` beside `connectionId` may change the header but stays inside the connection's own hosts and paths, so a saved key never reaches another host. The connection is found among the Agent's connections the member manages, never by an account id alone. A `path` that holds the key is refused. From Slack a key must be typed in the requester's own current message with every host and path it goes to, or come from the message that proposed a connection the requester approved in the last 30 minutes: a keyed connection on a host they did not type waits for their Approve click, no model turn follows the click, and the receipt says "Reply here and I’ll test the key you pasted." That window admits only the connection's first key since its last credential reset, and only while the connection still sends it inside the hosts and paths the approved change gave it, so an Admin edit since cannot move the key. The host reads that message from its own turn record over the state RPC, never from Slack, and stores nothing about the key. Slack allows 8 tries a turn, kept in the turn's persistent state; MCP allows 30 per member in 10 minutes through the auth rate limiter. A refused call keeps its try.

`disconnect_connection` disconnects one connection from an Agent through Admin's connection account service (`disconnectForAgent`): the account is revoked, its credential retired, and schedules that use it pause. A managed connection is removed as in Admin: Chickpea deletes the remote Composio account when no other Agent uses its sign-in, and keeps it while another does. A removal that fails before Chickpea asks Composio to delete the account, for example because Composio is not configured, leaves the connection and its schedules as they were. Once Composio was asked, a failure leaves the connection `needs_attention` with its schedules paused, so the Agent stops using it at once, and the call fails with `removal_incomplete` (5.0: `temporarily_unavailable`) saying a second removal finishes it. It names a connection by its id from the Agent's `connections`, `mcpServers` or `apiConnections`, so it also reaches the managed connections that only `connections` lists. It confirms on both doors, as Admin's "Disconnect account" does. It needs the right to edit the Agent, as the Agent page's Disconnect does. A team connection needs an Admin or Owner and a Member disconnects only their own; an Admin or Owner can also disconnect another member's personal connection when they name its account id (inspection never lists it).

A connection whose `lifecycle` is `needs_attention` carries a `reconnect` field in inspection when the requester may reconnect it: either a `prepare_connector_setup` call for a catalog connector, or a `request_setup` operation for the connection. Both reconnect the same account, as Admin's Reconnect does, so its bindings and Agent grants stay. On both doors, `prepare_connector_setup` issues a setup link fenced to that account (`replacement: true`). It does the same for a catalog sign-in left `pending`, such as one abandoned at the provider, so a new link finishes that connection instead of adding a second one beside it. Its result names the account in `reconnect`. On a one-connection page an MCP link opened, managed or catalog, Cancel posts `intent=cancel`: it cancels the link, so `get_setup_status` reads `cancelled` and the connect card says so, and ends on a page that says nothing was connected and to go back to the app, shown only to the link's person. A link whose sign-in is already being finished is left as it was. A Slack link's Cancel opens the Agent in Admin on a catalog page and starts the sign-in over on a managed one, and the waiting page's Start over keeps any link.

Each Agent's `websiteLogins` lists the website logins granted to it, in Admin's shape (`src/browser/agent-website-logins.ts`): site, label, owner, sign-in method, username, level, whether it is on, and when it was last used. It never includes a password or TOTP seed. Website logins belong to the team, so the owner is always `team`, and everyone who may edit the Agent sees every login on it, including a member's personal login saved before logins became team-only. Only an Owner or Admin may remove one: `remove_website_login` confirms as Admin does, and deletes the saved login once no Agent uses it. Capturing a login needs Admin's browser flow, so management cannot add one; `websiteLoginSetup` says an Owner or Admin adds it in Admin.

When access is missing, add `request_setup` for the exact Agent connection, repository grant, or model provider. Chickpea returns a URL whose fragment contains a one-use capability. It expires after 24 hours and may be cancelled with `cancel_setup_link` or reissued; reissue invalidates the prior link.

Anyone who can see the link can complete its exact frozen action without signing into Chickpea. Share it as a credential-bearing capability. The page shows the connector, target, requested scopes, and replacement warning. It cannot change those values. OAuth connections redirect to the provider; multi-field credentials use a Chickpea form. Validation clears submitted fields, activates the connection once, and creates a non-secret receipt. The receipt record holds the target, scopes, initiator, operation ID, and a provider-returned non-secret account label. A connection setup an Agent asked for from a Slack thread wakes that Agent there instead of posting a notice, so it tests the connection and continues. Otherwise the Slack notice shows only one plain line, such as:

```text
✅ Gmail (alex@northstar.example) is now connected to Customer Research.
```

Neither ever includes a token, code, key, client secret, header value, or repository installation credential.

## Models

`inspect_workspace` reports models the way Admin shows them. Its sources are Admin's own model pickers and checks (`src/config/model-choices.ts`, read through `src/management/model-sources.ts`), so the two cannot disagree.

- `modelCatalog` lists every model a person can pick in Admin now. `chat` holds the chat models of every provider the Workspace can run, whether through an API key, the ChatGPT plan, Workers AI, or Chickpea's models, each with the `efforts` it accepts in order (empty when the model has no effort setting). `image` holds the image models. Every actor gets it, Members included, because Admin shows the model pickers to anyone who can create an Agent. A model Admin's picker suggests but the Workspace cannot run, such as one the active catalog no longer serves, is left out.
- Each Agent carries its own pins (`model`, `modelEffort`, `imageModel`) in the shape the writes accept, and a read-only `effectiveModels`: the model, effort, and image model it runs, and whether each is `pinned` or follows the `workspace_default`. The effort follows the model: an Agent on the Workspace default model runs the Workspace default effort, and `null` is the model's standard effort.
- Owners and Admins also get `workspaceModels` with `chat` (the Workspace default model and effort), `image`, and `coding`, each with its revision (0 when it was never set). Members get neither `workspaceModels` nor `providers`, as Admin shows both only in Settings.
- Each `providers` row (`anthropic`, `openai`, `openrouter`, and `workers-ai` except on a deployment serving many installations, as on Admin's Providers page) says whether that provider's models can run now (`available`) and how (`access`: `api_key`, `chatgpt_plan`, `workers_ai`, or `platform` for Chickpea's models), as Admin's model picker decides it. `source` and `mutable` describe only the API key, so a Workspace on its ChatGPT plan reads `available: true`, `access: "chatgpt_plan"`, `source: "missing"`. Workers AI has no key; its `source` is `env` when the deployment provides it and Admin has it turned on.

Two operations change models with Admin's authority and checks:

- `set_workspace_model` sets the `role` `chat` (the Workspace default), `image`, or `coding` to `model` at the role's `expectedRevision` from `workspaceModels`. `modelEffort` applies to `chat` and `coding`; omitting it runs the model's standard effort. `model: null` clears the image or coding model; the chat default cannot be cleared. Only Owners and Admins may change a Workspace model. Admin asks nothing first, so over MCP it applies at once. In Slack it changes every Agent that follows the Workspace, so it waits for the person's approval (`workspace_model_change` in `POSTURE`). Undo puts back the previous model and effort, except for a chat default that was never chosen.
- `set_agent_image_model` pins an Agent's image model, or with `null` follows the Workspace image model, at the Agent's `expectedRevision`. Anyone who may edit the Agent can change it, Members included, and it applies at once on both doors with an undo, like any one Agent field.

A refused choice fails with Admin's own words in `instruction`, for example "openai/gpt-6.1-sol is not an image model.", "Add an OpenAI API key before choosing openai/gpt-image-2.5-flare.", or an effort the model lacks (`effort_not_supported`). A change set previews each as a before and after, for example **Workspace — Default model** and **Research — Image model**. `tests/management-model-policy.test.ts` covers inspect, both operations on both doors, Members, the Slack approval, and undo.

## Memory, routines, and team

Agent memory uses the Agent owner scope and expected version. Inspection returns active entry bodies only to a member who can edit that Agent; forgetting applies at once and can be undone. A turn already running keeps the memory it read, so its reply may still post; the next turn reads memory fresh. Channels do not own instructions or memory. Routine inspection and mutation are filtered through the same Agent edit policy and preserve content authority, while routine save/control/delete retain the existing schedule and version contracts. As in Admin, a member edits, runs, pauses, resumes, or deletes a Channel routine only when they can read it (Slack shows them in its private Channel), and only Owners and Admins disable one. A member creates a Channel routine in a private Channel only while Slack shows them in it. Saving, editing, or reassigning a DM routine needs the private use the person would need to DM its Agent, and every run checks that use again. When Slack cannot answer, a save fails with `slack_unavailable` rather than a refusal, and a run counts the failure toward the three that pause the routine instead of disabling it. A member's inspection lists a private Channel only while Slack shows them in it.

Over MCP, `list_schedules` also lists the signed-in person's own DM routines and never another person's, an Owner's included. A DM routine's `destination` is `direct_message` with a label such as "your DM with Support", and its `channelId` is null. The person pauses, resumes, edits, runs, or deletes it as they could in that DM; an edit keeps its Agent. Creating a DM routine still needs the trusted Slack DM, and only Chickpea in that DM changes a DM routine's Agent, so no MCP tool changes it: Admin cannot change a routine's Agent either. A Channel routine whose Runs as authority broke is repaired with `take_over_schedule` over MCP, through Admin's Runs as repair route (`POST /admin/api/agents/:id/schedules/:scheduleId/reassign`): an editor of the routine's Agent becomes its Runs as member, its connection accounts are re-selected or must still be eligible for them, and a pause its authority caused resumes. As for every other routine change, a member must also be able to read the routine. Inspection returns `pausedReason` and `disabledReason`, and a paused or disabled routine has no `nextRunAt`. A routine's name and task follow Admin's content rule: they show when its Channel is public or Slack shows the person in it, and in a Slack Channel conversation only for that Channel's own routines. A member's `inspect_workspace` adds `usableAgents`, the Agents they may DM and so schedule DM work with, with `canEdit` marking the ones `agents` lists.

Eligible full Slack members are provisioned automatically the first time they interact with an Agent. Guests and Slack Connect users are not provisioned. A full member can create an Agent and inspect or mutate only Agents allowed by that Agent's edit policy. Owners and Admins see the team list in `inspect_workspace`, as Admin shows them the Team page; only Owners change an existing membership's role or status. Provider inspection, the Workspace models, and provider mutations remain Admin/Owner-only; provider results expose availability and affected Agents, never a key or environment-secret value. Deployment-provided credentials are visibly read-only.

## Run history

`list_agent_runs` and `get_agent_run` (`src/management/mcp-v5/run-history.ts`) return two kinds of run: the caller's own 1:1 direct messages with an Agent, and the Agent's runs in public Slack Channels. Other people's direct messages, group DMs and private Channels never leave, for an Owner or Admin too. Neither tool reads a run's raw tool results, the work ledger's copy of a message, or a Help-improve copy, and a test fails if the module graph reaches `src/review/`.

- **Index.** The usage ledger's `interactive_turn` operations for the Agent, at most 90 days back, read from the start of the UTC day of `since`. The query itself holds only runs the caller could be shown (`UsageQuery.runHistory`): their own 1:1 DMs and Channel runs, and for a member who cannot change the Agent only the public Channels Slack shows them in. So the read limit of 1,000 runs a call, `partial`, `nextCursor` and a page's edge say nothing of other people's DMs, group DMs, or Channels the member cannot see. The query only narrows; every run it returns is judged again below. Someone who can change the Agent still reads every Channel run, private ones included, and is told how many are hidden in whole days (`notShown`). So when the limit cuts their first page part-way through a UTC day, the page keeps the whole days it read and leaves that day to the next page: what they see then moves when the limit crosses a day, never as each hidden run arrives. An Agent with more than 1,000 such runs inside one UTC day has no whole day to keep, and there the cut still moves run by run.
- **Schedules, not yet.** The list reads no `routine_run`: on Cloud a Channel schedule run has no ledger run, so `getRunVisibilities` can never confirm it public, and listing only DM schedules would read as if Channel schedules never ran. `place: schedules` returns no runs, no `summary` and a `note` that schedule runs aren't listed yet, and no count includes them. `get_agent_run` still judges a schedule run's `runId` from an earlier list as below.
- **Own DM.** The run is a direct message, the caller asked it (or a DM schedule runs as them), and its channel ID starts with `D`. Usage records a group DM as a direct message too, so the prefix keeps it out.
- **Public Channel.** The ledger recorded the run public (`getRunVisibilities`, as Admin's Usage page reads it), and Slack says now that the Channel is public, not shared beyond the workspace, and still has Chickpea's app in it. Chickpea's app is the one that counts, even for an Agent with its own Slack app: only Chickpea's app subscribes to Channel messages (`message.channels`, `message.groups`), so only while it is in a Channel do Slack's deletions reach the thread record. A member who cannot change the Agent also needs Slack's directory to show them in the Channel. A Channel or directory that Slack cannot describe hides the run.
- **Every call decides again.** A `runId` is the usage operation sealed with AES-GCM under a key derived (HKDF-SHA-256, info `chickpea-run-history-handle:v1`) from the deployment's Better Auth secret and salted with the installation. `get_agent_run` checks the Agent and the run again, so a handle stops working when the caller loses either. The cursor is sealed the same way. The IV is synthetic, an HMAC (HKDF info `chickpea-run-history-iv:v1`) of everything sealed, so one run has one `runId` on every list. A cursor can hold the place of a run the caller is not shown, so it carries a nonce of its own and is padded to one length: no two cursors are equal, and none tells someone who polls that a hidden run arrived.
- **Words.** An ask and a reply come from the thread record, which applies Slack's edits and deletions. A message that is gone reads as `not_kept`, ask and reply. So does one Slack replaced with its "This message was deleted." placeholder, which it does when the deleted message has replies and sends as an edit. When another run of the Agent answered the same message within a day, the reply reads as `not_kept` too, because the record cannot say whose it is. That check reads only runs the caller could be shown, so other people's DMs never decide it. The list shows the start of an ask only on runs the caller asked. Text that looks like a key is redacted. A schedule run has no ask, and its reply is `not_kept`.
- **Counts and cost.** The summary counts only runs the caller sees. Someone who can change the Agent also gets `notShown`, the hidden runs counted in whole UTC days before today, never another person's DM schedule. `charged` appears on the caller's own runs, and on every run for an Owner or Admin: the bill where the deployment has one, else a list price estimate. The bill leaves out a run whose rows net to nothing, so a run it was read for and does not name reads `$0`; a run with no billing key, or a bill that can't be read, shows none.
- **Size.** Slack's words appear once, in `structuredContent`. The text block holds counts and handles. The whole result is at most 28,000 UTF-8 bytes; the reply is cut at 6,000 characters, the ask at 2,000.

## Portable recipes

`export_workspace_recipe` returns a schema-versioned, immutable result for selected Agents. Version 2 contains the name, description, edit policy, instructions, enabled state, model and reasoning effort, inline skills with their import or suggestion provenance, connection requirements, and repository requirements. A repository requirement names one repository (`fullName`) or every repository of one GitHub account (`owner` with `allRepos: true`). Preview also accepts version 1 recipes. The export deliberately excludes:

- workspace and Channel IDs;
- members and member mutations;
- Slack identity and provider account identifiers;
- credentials, OAuth codes/tokens, and secret-bearing URLs;
- repository installation IDs;
- connection status and tool policies; and
- Agent memory and Channel publication grants.

`preview_workspace_recipe` compares the recipe with current state. Name conflicts return `clone`, `update`, and `skip`; duplicate matches return `ambiguous`. Unsupported versions, malformed requirements, duplicate symbols, unsafe URLs, unsupported model providers, and batches over 25 operations fail before any write.

Each new or cloned Agent compiles to a base `create_agent` with no connections or repositories, then one `update_agent` with `expectedRevision: 0` that adds them and applies a disabled state, then one `request_setup` per connection, repository, or model provider that still needs a credential. An overwrite compiles to one `update_agent` with `recipe_overwrite`. Setup is decided by the same server-owned rules as the write, so an overwrite issues no link for a connection that keeps its working credential. A recipe never binds a GitHub installation, because recipe data is untrusted. A named repository becomes a grant with no installation plus a setup link. An all-repositories requirement creates no grant; preview lists it under `setupRequired`, and the person grants it in Admin. An overwrite keeps, unchanged, a grant the Agent already holds under the same id for the same repository or account.

In Slack, apply the returned `operations` unchanged in one `apply_workspace_changes` call. Over MCP, `export_agents` exports a recipe and the 5.0 writes make each change. There is no separate recipe authority or background reconciliation. Each item passes its own policy. In Slack, the call creates each bare Agent at once and holds its capabilities and overwrites in a change set for the person's approval. It issues no setup link; the approval's receipt carries the links. When a recipe creates several Agents, that approval creates the later ones without their capabilities or setup links, which need a new request; the call reports those setup items as `dependency_not_applied`. Expected revisions ensure a live edit made after preview wins and forces a new preview.

## Operation polling, receipts, and revocation

Every mutation has a durable operation ID. The Slack door's `get_operation`, and `get_setup_status` over MCP, return only records owned by the same requester and organization. Setup URLs are returned once when issued and are not stored in pollable operation results. Polling reveals lifecycle and non-secret receipts, not raw capabilities.

Exact proposals return a bounded preview, missing-setup list, target revisions, and canonical guide metadata. The rendered preview (`presentation.slack` and `presentation.markdown`) comes from `src/management/change-set-presentation.ts`. It shows only the record fields in its `PRESENTATION_FIELDS` allowlist. An operation whose records mean nothing to a person, such as an archive, restore, delete, member change, provider key removal, Channel reach change or routine action, renders as one sentence from the change's `statement`, which the service resolves when it freezes the set: names, the @handle, the Channels an archive leaves, and the Agents and Workspace image and coding models a provider key removal affects. A Channel the Agent gains after the preview makes an archive, delete or disable stale, so the person approves a fresh count. Connection changes name the connection and the Agent, and a routine's destination names its Channel. IDs, Slack presence, avatar seeds, revisions and lifecycle internals never render. Every `failed` or `skipped` outcome carries `instruction`, a short explanation for the model: the message of a `ManagementError` or `AgentPresenceError`, or a fixed line for a code-only outcome. Confirmation results report `applied`, `setup_required`, `stale`, `denied`, `failed`, or `partial` outcomes without returning authored bodies in telemetry. A result whose every item failed or was skipped reports top-level `failed`. A `partial` result means the admitted change set encountered a downstream per-item failure after an earlier item applied; dependents are skipped and the receipt identifies item and operation classes. It is not permission to replay the whole set.

A preview that must be cut to fit Slack or Markdown keeps every part that widens access, and cuts only parts that grant nothing. When the widening parts alone cannot fit in one preview, the service refuses the proposal with `invalid_request` and "The access this proposal grants is too long to show in one preview. Split it into smaller proposals." A reviewed proposal whose operations and diff together exceed 1.5 MiB is refused the same way. Very large proposals can reach these limits on either door, for example a recipe that updates 20 Agents and their connections in one call. Over MCP this happens when a destructive item holds the rest of its call in one change set. Send such a change as several smaller calls.

`undo_change` (`undo_workspace_change` in Slack) is available only for an eligible single safe mutation while its target still holds what the change left, and for 30 days: retention then deletes the undo record, used or not, because it can hold what the change replaced, such as forgotten memory. An Agent edit's undo puts back exactly the fields the edit set, plus the effort a model change dropped, so its policy classifies the undo by what it changes: a one-field undo applies at once, and an undo that removes a connection asks first. Slack presence sync advances the Agent's revision after a name, description or handle change without changing what people configure, so the undo record keeps a digest of the Agent's configuration and compares that instead of the revision; anyone else's edit to the Agent still makes the undo `proposal_stale`. Other undos compare exact revisions. A call whose one change waited for confirmation over MCP or approval in Slack gets the same undo once that change applies (`offerUndo` in `src/management/service.ts`); `undo_change` accepts the call's `undoToken`, which is its `operationId`, or the confirmation's. Slack requires an explicit undo request, and other inverses still use Slack's consequence-based policy. Over MCP the inverse applies directly unless it is destructive, in which case undo returns `needs_confirmation` instead of bypassing confirmation.

## Diagnostics and telemetry

Content-free log envelopes use the `[chickpea:management]` prefix. Events cover OAuth discovery/DCR/token/request outcomes, tool calls, operation kind and disposition, Agent-authoring guide version, posture, artifact class, proposal outcome, stale reason, handoff class, setup lifecycle, receipt delivery, live-versus-snapshot admission, and recipe preview counts. Dimensions are fixed machine tokens and counts; unknown values become `other`. Actor IDs, Slack coordinates, object IDs, names, prompts, instructions, memory bodies, recipes, repository names, URLs, account labels, credentials, setup capabilities, and error text are not accepted.

Each JSON-RPC message `/mcp` handles emits one `mcp.request` event, one per member of a batch:

| Field | Value |
| --- | --- |
| `method` | The JSON-RPC method, such as `initialize`, `tools/list`, `tools/call`, `resources/read`, `prompts/get`, or `notifications/initialized` |
| `tool` | For `tools/call`, the tool name, a removed 4.x tool's included; any other name is `other` |
| `resource` | For `resources/read`, `chickpea://guide/discovery/v1`, or one of the removed `chickpea://guide/agent-authoring/v1`, `chickpea://schema/operations/v2` and `chickpea://workspace`; any other URI is `other` |
| `outcome` | `success`; `tool_error` (an `isError` result from the handler); `input_refused` (the SDK refused the arguments on the tool's input schema, so the handler never ran); `jsonrpc_error`; `received` (a notification); or `abandoned` (no response was sent before the connection closed: the client disconnected, cancelled the request, or the SDK dropped it) |
| `errorCode` | For `jsonrpc_error`, the JSON-RPC code, such as `-32602` |
| `durationMs` | From the message's arrival to its response; absent for a notification |

An `input_refused` call has no `tool.call` event. It emits `tool.validation_failure` with `surface: "mcp"`, the same event the Flue surface emits, carrying `tool`, `fields`, and `validationCodes` (zod issue codes). Each field is a path of schema property names and array indexes, such as `operations.0.expectedRevision`; any other key becomes `*`. To tell a refused call from a read, query `mcp.request` by `method` and `outcome`, then `tool.validation_failure` for the failing field. Requests the OAuth check refuses before the server runs appear only as `oauth.request`.

For support:

1. Confirm `/.well-known/oauth-protected-resource/mcp` names the exact `/mcp` resource and `/api/auth` authorization server.
2. A `401` without a token must include a protected-resource challenge. A `403` after authorization usually means the live Chickpea membership, role, or scope no longer permits access.
3. Inspect the operation by ID. `confirmation_required`, `setup_required`, `skipped`, and `failed` are item dispositions, not transport failures.
4. For a setup problem, check whether the link is expired, revoked, exchanged, completed, or stale. Reissue rather than sharing browser cookies or credentials.
5. Use content-free event/reason tokens from logs. Do not add response bodies, OAuth queries, setup URLs, recipe JSON, or Slack messages to diagnostics.

## Canary and rollback

Live deployment and third-party mutation require explicit authorization. In a disposable workspace:

1. Record the deployment revision and keep `CHICKPEA_LIVE_CHANNEL_CONFIG` unset.
2. Connect one supported client, inspect the workspace, and make one reversible instruction edit on a canary Agent.
3. Hold one Slack response in flight, apply a second edit, and prove the held response finishes with its admitted revision while the next message in the same thread reports the new effective revision.
4. Reassign the canary Channel and prove bounded Slack history is rehydrated without a fresh-context notice.
5. Exercise one delegated setup against a disposable provider account, verify the original thread/DM receipt, then revoke the connection.
6. Set `CHICKPEA_LIVE_CHANNEL_CONFIG=false`, redeploy, and prove a new Channel root uses a write-once snapshot while already admitted TurnJobs remain unchanged. Unset it and redeploy to restore next-turn live resolution.
7. Disconnect and reconnect the MCP client; confirm the same live Slack membership is required and stale tokens cannot bypass suspension or removal.

The public management surface can be disabled operationally by removing its route at deployment or rolling back the artifact. Do not delete OAuth or management state during rollback: already admitted TurnJobs, durable operations, proposals, setup revocation, and receipts must remain explainable.
