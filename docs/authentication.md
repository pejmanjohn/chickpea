# Authentication and authorization

Chickpea has one human identity path: Slack OpenID Connect. Better Auth stores the provider account and opaque browser session. Chickpea owns the workspace binding, members, roles, invitations, authorization overlays, setup and recovery capabilities, and audit history.

## First Owner

A fresh deployment starts `unconfigured` and exposes only the private seven-day setup capability generated by the deploy command. The default setup journey asks the installer to generate a short-lived Slack App Configuration access token from [Your App Configuration Tokens](https://api.slack.com/apps#:~:text=Your%20App%20Configuration%20Tokens); Chickpea sends that token to Slack once and never stores it. Slack also displays an `xoxe-` refresh token, which Chickpea does not need.

If the installer cannot create an App Configuration token, **Can't create an app configuration token?** opens `/admin/setup/manual` in the same browser tab. That separate journey restores the original manifest, Slack Event Subscriptions, and app-credential walkthrough. It accepts App ID, Client ID, Client Secret, Signing Secret, and the exported JSON manifest—but never a pasted bot token. Both paths then use the same confidential bot OAuth, signed Events proof, exact installer binding, and Slack OIDC first-Owner claim. Submitted credentials are encrypted before persistence, and validation errors clear every write-only field.

The setup journey installs the customer-owned app to one exact Slack workspace, validates the issued bot token and exact scope set, and requires a signed Events API challenge before promoting the encrypted credential revision.

The installer then completes Sign in with Slack. Chickpea compares the exact OpenID Connect `team_id` with the installed workspace and atomically binds the installer's Slack `user_id` as the first Owner. Slack may allow an ordinary member, admin, or owner to install depending on that workspace's own app-management policy; Chickpea does not impose a second workspace-role requirement.

## Normal sign-in

`/auth/slack/sign-in` starts a confidential Slack OIDC flow using `openid profile`, a browser-bound hashed state, a nonce, and the exact installed workspace. The callback exchanges the code with `client_secret_post`, validates issuer, audience, nonce, token type, team, and user, then creates the Better Auth provider account/session only after Chickpea admission succeeds.

A valid Slack identity is not sufficient by itself. Each Admin request re-resolves the canonical `(team_id, user_id)` binding and requires an active Chickpea membership. Suspended, removed, mismatched-workspace, and uninvited people receive a uniform denial and no session authority.

## Invitations and roles

Control-plane access is invitation-only after bootstrap. An Owner creates a seven-day invitation for an exact Slack `team_id` and `user_id`; the capability is shared privately and stored only as a digest. Redemption requires a fresh OIDC proof for that same tuple. Reissue invalidates the prior link, and expiry, revocation, mismatch, and replay fail closed.

Chickpea roles are `owner`, `admin`, and `member`. Slack workspace roles do not grant Chickpea permissions. The last active Owner cannot be demoted, suspended, or removed. Session and personal-token authority is revoked when membership authority changes.

Members of assigned Slack channels may interact with Agents without control-plane membership. Chickpea membership governs the Admin control plane and future MCP administration, not ordinary channel conversation.

## Secrets and recovery

`CHICKPEA_AUTH_SECRET` is independent 32-byte key material used for Better Auth sessions. `CHICKPEA_RECOVERY_TOKEN` is a separate optional deployment capability for the hidden Slack credential-repair path; it never signs a session or creates a member. Slack client, signing, and bot secrets are AES-GCM encrypted in `TAG_STATE` with an independent versioned credential keyring. Runtime environment fallback for Slack credentials is not supported.

Recovery is limited to the unchanged Slack app and workspace. A 15-minute browser-bound grant may stage a replacement encrypted revision, but promotion still requires OAuth validation and a revision-bound signed Events proof. Recovery cannot create an Owner, change a role, bind a different app/workspace, or sign anyone in. See [Slack authentication recovery](runbooks/slack-auth-recovery.md).

## Deployment database

Cloudflare deployments require the exact `AUTH_DB` D1 binding and the reviewed fresh Better Auth schema. Deploy stops before upload if the binding would be omitted, replaced, split, or if the database contains an incompatible `0001`. There is no migration path from password, Cloudflare Access, or shared-token installations; use a fresh deployment. See [AUTH_DB deployment contract](runbooks/auth-db-deployment.md).
